# Resolve stable FactSlot identity

**Story ID:** F0007-S0001
**Feature:** F0007 — FactSlot model
**Title:** Resolve stable FactSlot identity
**Priority:** Critical
**Phase:** MVP
**Status:** Done

## User Story

**As a** Ingrid the Persistence Engineer
**I want** every semantic question about a subject to resolve to exactly one FactSlot identity in its knowledge base
**So that** two limits that differ only by basis never share an answer and the same question never splits into two slots.

## Context & Background

ADR-0006 makes FactSlot first-class; master blueprint §13 gives the scalar example and §109.1 lists the identity rules still to specify. G1 (2026-11-09) chose an opaque, versioned predicate key: F0012/F0013 register real predicates later, and ADR-0038's SourceAuthorityPolicy keys on the same predicate key.

## Acceptance Criteria

- [ ] **AC1:** Given subject S, predicate key `hasLimitAmount` with pinned release R, and qualifiers `{basis: EachOccurrence, currency: USD}`, resolving twice, including from two concurrent sessions, returns the same slot ID and leaves exactly one slot with one set of qualifier rows.
- [ ] **AC2:** Changing only `basis` to `GeneralAggregate` resolves a different slot (ADR-0006 use case). Supplying the same qualifiers in a different input order resolves the original slot.
- [ ] **AC3:** Qualifier values are normalized by declared type before identity: Unicode NFC for text and one canonical decimal encoding (`1000000`, `1000000.00` and `1E+6` are equal). The normalized qualifier rows are stored and the fingerprint records its algorithm version. If two different normalized qualifier sets ever produce the same fingerprint, the second is rejected with `FINGERPRINT_COLLISION` and the slots are not merged.
- [ ] **AC4:** An omitted qualifier and a qualifier supplied as explicit null follow one documented rule (settled in Phase B). Fixtures prove the rule's outcome for both inputs, and neither input is silently coerced into the other.
- [ ] **AC5:** For a tenant entity associated with KB A and KB B, the same predicate key and qualifiers resolve to two distinct slots, one owned by each KB. A principal authorized only for KB B is denied resolution or reads of the KB A slot, and the denial is indistinguishable from not found.
- [ ] **AC6:** A malformed predicate key, or one with no pinned release reference, is rejected with `PREDICATE_KEY_INVALID` and no slot row is written. The resolved slot exposes its predicate key unchanged for SourceAuthorityPolicy lookup. F0007 does not check predicate semantics against an ontology.
- [ ] **AC7:** Creating a slot is authorized against the caller's existing KB write authority (F0002). Each creation writes one audit event naming actor, tenant, KB, slot ID and fingerprint version. Unauthorized or cross-tenant subject attempts are denied with zero slot rows. Updating identity fields after creation is rejected.

## Interaction Contract

| Surface / Entry Point | User Action | Editable State | Save / Mutation Result | Reload / Persistence Evidence | Roles / Status Constraints |
|---|---|---|---|---|---|
| Internal slot-resolution service (engine) | Resolve or create a slot from subject, predicate key and qualifiers | New slot only; identity immutable once created | Returns existing or newly created slot ID; audit event on create | PostgreSQL reload returns the same ID and normalized qualifiers; concurrent test shows one row | Existing KB write authority to create; read authority to resolve an existing slot |

No new screen or HTTP route. Tests must exercise the resolution service against PostgreSQL, not only the fingerprint function.

## Data Requirements

Tenant, KB, subject entity identity, predicate key and release reference, cardinality (S0002), normalized typed qualifier rows, fingerprint and algorithm version, creation actor and time.

## Role-Based Visibility

Only principals authorized for the slot's KB can resolve or read it. Denials do not reveal whether a slot exists in another KB or tenant.

## Non-Functional Expectations

Deterministic identity with no model call and no clock dependence. The resolve-or-create step is idempotent and safe under concurrent callers.

## Dependencies

F0002 tenant entity identity, authorization and audit. F0003 persistence conventions. The F0001 pilot `fact_slot` table. S0002 supplies cardinality and S0006 supplies legacy compatibility.

## Out of Scope

Fact versions and time (F0008), ontology validation of predicates (F0012/F0013), entity resolution (F0017), SourceAuthorityPolicy evaluation (F0018).

## Questions & Assumptions

G1 decided the predicate key form. The Architect owns the canonical encoding, the hash function and the omitted-versus-null rule. Assumption: slots are KB-owned semantic content (ADR-0061, ADR-0066 §1a).

## Definition of Done

- [ ] Seven ACs pass against PostgreSQL, including the concurrent and cross-KB negative fixtures.
- [ ] Normalization and fingerprint rules are documented with worked and boundary examples.
- [ ] Feature action records tests, coverage and required signoffs.
# Distinguish single, multi-valued and relationship slots

**Story ID:** F0007-S0002
**Feature:** F0007 — FactSlot model
**Title:** Distinguish single, multi-valued and relationship slots
**Priority:** Critical
**Phase:** MVP
**Status:** Done

## User Story

**As a** Ingrid the Persistence Engineer
**I want** each slot to declare whether it holds one answer, a set of members, or a relationship to another entity
**So that** two additional insureds coexist and removing one can close only that membership.

## Context & Background

Master blueprint §109.1: the single-valued overlap constraint (§15) must not be applied unchanged to a set of legitimate insureds or locations, and relationships need explicit identity. F0008 owns temporal versions and the close operation. F0007 defines the identity unit those versions attach to.

## Acceptance Criteria

- [ ] **AC1:** Every slot has a cardinality of `SINGLE`, `MULTI` or `RELATIONSHIP`, fixed at creation from the predicate contract. Resolving an existing identity with a different cardinality is rejected with `CARDINALITY_CONFLICT` and writes no rows.
- [ ] **AC2:** For a `SINGLE` slot, a second fact version that overlaps an existing version in both valid and recorded time is rejected by the existing ADR-0008 exclusion constraint (pilot regression).
- [ ] **AC3:** For a `MULTI` slot, each member has its own member identity derived from its normalized value or member entity identity. Two different additional insureds give two members under one slot. Asserting the same insured twice resolves to the one existing member. Overlap is enforced per member, so the second insured is not rejected.
- [ ] **AC4:** A `RELATIONSHIP` slot's identity is subject, predicate key, object entity identity and qualifiers, so two relationships that differ only in object are distinct. An object outside the slot's tenant, or not associated with the slot's KB, is rejected with `RELATIONSHIP_OBJECT_OUT_OF_SCOPE`.
- [ ] **AC5:** §109.1 identity fixture: with members A and B in one `MULTI` slot, a version change addressed to member A references no row of member B. F0008 proves the temporal close.
- [ ] **AC6:** An unknown cardinality, a `MULTI` member with no member key, or a `RELATIONSHIP` without an object is rejected with a named reason and zero rows. Creating a member writes an audit event with actor, slot and member identity, and unauthorized member creation is denied.

## Interaction Contract

| Surface / Entry Point | User Action | Editable State | Save / Mutation Result | Reload / Persistence Evidence | Roles / Status Constraints |
|---|---|---|---|---|---|
| Internal slot-resolution service | Resolve a slot, member or relationship | New identities only; cardinality immutable | Returns slot/member identity; audit event on create | Reload shows one member per distinct insured and per-member overlap scope | Existing KB write authority |

No screen. Member identity is storage and contract only; F0008 owns temporal behaviour.

## Data Requirements

Cardinality enum, member key and member entity reference, relationship object entity identity, and tenant/KB ownership on each member and relationship row.

## Role-Based Visibility

Members and relationship objects are visible only through the parent slot's KB authorization. An object entity outside the reader's grants is not disclosed.

## Non-Functional Expectations

Deterministic member identity with no model call. Per-member uniqueness is enforced by the database, not only by application code.

## Dependencies

S0001 slot identity, F0002 entity identity and KB associations, and the existing ADR-0008 constraint from the F0001 pilot. F0008 consumes member identity for temporal versions.

## Out of Scope

Temporal close and supersession (F0008, F0019), relationship ontology (F0012/F0013), relationship resolution from documents (F0016/F0017), and graph projection (F0034).

## Questions & Assumptions

The Architect decides whether member identity is a child row of the slot or a slot-level key, provided the ADR-0008 constraint applies per member. Predicate cardinality comes from the predicate contract (S0001) or the F0007 system-predicate set (S0005).

## Definition of Done

- [ ] Six ACs pass against PostgreSQL, including the two-insureds fixture and the cardinality conflict.
- [ ] Feature action records tests, coverage and required signoffs.
# Carry information state separately from value

**Story ID:** F0007-S0003
**Feature:** F0007 — FactSlot model
**Title:** Carry information state separately from value
**Priority:** Critical
**Phase:** MVP
**Status:** Done

## User Story

**As a** Rosa the Business Reviewer
**I want** each FactSlot answer to state whether the information is present, not processed, not found in a named scope, not stated, illegible, ambiguous, conflicting, explicitly negative or not applicable
**So that** "not found on pages 1–3" is never read as "the policy has no aggregate limit".

## Context & Background

ADR-0039 decisions 1–3 and master blueprint §107.4. F0007 is the carrier. F0008 versions it bitemporally, F0016 records the scope its runs searched, and F0020/F0023 return and display it. EX-OWN-003 is the worked example.

## Acceptance Criteria

- [ ] **AC1:** The answer carrier accepts exactly `PRESENT` and the eight ADR-0039 states (`NOT_PROCESSED`, `NOT_FOUND`, `NOT_STATED`, `ILLEGIBLE`, `AMBIGUOUS`, `CONFLICTING`, `EXPLICIT_NEGATIVE`, `NOT_APPLICABLE`). Any other state is rejected with `INFORMATION_STATE_INVALID`. No access-denied or restricted state exists.
- [ ] **AC2:** Only `PRESENT` carries a value. A value on any other state, or `PRESENT` with no value, is rejected with `STATE_VALUE_MISMATCH` and no fact version is written.
- [ ] **AC3:** `NOT_FOUND` and `NOT_STATED` require a scope naming the content artifact version, the profile release reference and the pages or blocks covered. A missing or empty scope is rejected with `ABSENCE_SCOPE_REQUIRED`. A scope reference outside the slot's tenant/KB is rejected.
- [ ] **AC4:** Reading a slot, or a resolvable slot key, that has no recorded answer returns `NOT_PROCESSED`. It never returns null or an empty body.
- [ ] **AC5:** EX-OWN-003: `NOT_PROCESSED`, `NOT_FOUND` (pages 1–3) and `NOT_STATED` (reviewed scope), each committed through the existing pilot commit path, reload as three distinguishable answers with their scopes intact. F0008 owns how a later answer supersedes an earlier one.
- [ ] **AC6:** A principal without read authority over a scope's content receives an authorization denial before any missingness explanation. No state answer exposes block IDs, page numbers or excerpts from a scope the principal is not authorized to read (threat T-08).
- [ ] **AC7:** Each accepted state answer is recorded under the existing commit audit. A rejected carrier produces no fact version, and the rejection reason is returned to the caller.

## Interaction Contract

| Surface / Entry Point | User Action | Editable State | Save / Mutation Result | Reload / Persistence Evidence | Roles / Status Constraints |
|---|---|---|---|---|---|
| Existing canonical commit boundary (pilot) and slot read | Submit a state answer; read a slot | New answers only; prior answers untouched | Fact version with state, value or scope; audit via commit | `GET /facts/{factSlotId}` reload returns the state and scope; an unread slot reads `NOT_PROCESSED` | Existing commit and read authority; denial before explanation |

No new screen or route. Reviewer display is F0022/F0023.

## Data Requirements

State enum, optional typed value (S0004), and absence scope (content artifact version ID, profile release reference, page/block list) bound to the slot's tenant/KB.

## Role-Based Visibility

Scope details are visible only to principals authorized for that content. Access denial is decided by authorization and never encoded as an information state.

## Non-Functional Expectations

Validation is deterministic and runs at the boundary before any write. An invalid carrier causes zero partial writes.

## Dependencies

S0001 slot identity, S0004 typed values, the F0001 pilot commit path and F0004 content artifact identities. F0008, F0016, F0020 and F0023 consume the carrier.

## Out of Scope

Producing `NOT_FOUND` scopes from runs (F0016), bitemporal supersession of states (F0008), package completeness (F0014), and user-facing display (F0020/F0023).

## Questions & Assumptions

Assumption: an unread slot answers `NOT_PROCESSED` at read time, with no stored row per possible slot. The Architect decides where the carrier is persisted on the F0008-owned version row without breaking pilot reads.

## Definition of Done

- [ ] Seven ACs pass with positive and negative carrier fixtures and the EX-OWN-003 sequence.
- [ ] Feature action records tests, coverage and required signoffs.
# Type money and identifiers

**Story ID:** F0007-S0004
**Feature:** F0007 — FactSlot model
**Title:** Type money and identifiers
**Priority:** Critical
**Phase:** MVP
**Status:** Done

## User Story

**As a** Priya the GL Underwriter
**I want** limits held as exact amounts with currency and basis, and identifiers held with the scheme that issued them
**So that** a USD 1,000,000 each-occurrence limit is never confused with an aggregate limit or with another carrier's policy number.

## Context & Background

ADR-0039 decisions 4–5 and master blueprint §107.3. F0011 publishes the JSON Schemas, F0013 applies these types to GL limits, and F0017 resolves on scoped identifiers. Acceptance example (§107.3): two carriers use the same policy number, so the Brain holds two policies.

## Acceptance Criteria

- [ ] **AC1:** A money value is an exact decimal amount, an ISO 4217 alphabetic currency code and, where the predicate requires one, a basis qualifier. A binary floating-point amount is rejected with `MONEY_FLOAT_REJECTED`. An unknown currency code is rejected with `CURRENCY_INVALID`. A missing required basis is rejected with `BASIS_REQUIRED`.
- [ ] **AC2:** `1000000`, `1000000.00` and `1E+6` in USD compare equal and serialize to one canonical form. Round trips through PostgreSQL lose no precision for `0.01`, `999999999999999.99` and an amount above 2^53.
- [ ] **AC3:** F0007 accepts original-currency money only. A value marked as converted is rejected with `CONVERTED_MONEY_UNSUPPORTED` until a feature owns exchange-rate provenance.
- [ ] **AC4:** A scoped identifier is (scheme or issuer, identifier type, value, optional effective interval). Policy number `GL-1001` from carrier A and `GL-1001` from carrier B are two different identifiers. An identifier with no scheme is rejected with `IDENTIFIER_SCHEME_REQUIRED`.
- [ ] **AC5:** Value normalization is declared per identifier type. FEIN `12-3456789` and `123456789` compare equal. No normalization ever makes identifiers from different schemes equal.
- [ ] **AC6:** Money and identifiers used as qualifiers or member keys contribute their canonical encoding to slot identity, so equal values resolve one slot or member (S0001/S0002).
- [ ] **AC7:** An unauthorized caller is denied before any value-validation detail is returned. A rejected value produces no slot, member or fact version. Accepted values are recorded under the existing commit or slot-creation audit.

## Interaction Contract

| Surface / Entry Point | User Action | Editable State | Save / Mutation Result | Reload / Persistence Evidence | Roles / Status Constraints |
|---|---|---|---|---|---|
| Slot resolution and existing commit boundary | Submit a typed value or qualifier | New values only | Canonical value stored, or a named rejection | Reload returns the identical canonical amount, currency, basis and identifier tuple | Existing KB write/commit authority |

No screen or route.

## Data Requirements

Decimal amount, currency code, basis, identifier scheme or issuer, identifier type, identifier value and optional effective interval, each carried in canonical encoding.

## Role-Based Visibility

Typed values inherit the visibility of their slot and KB. No extra exposure is introduced.

## Non-Functional Expectations

No binary floating point in any authoritative path. Encoding is deterministic and locale-independent.

## Dependencies

S0001 identity encoding, S0003 carrier, and the F0001 pilot commit path. F0011, F0013 and F0017 consume these types.

## Out of Scope

Currency conversion and exchange rates, GL basis vocabulary (F0013), exposure units, financial-component formulas, and identity resolution on identifiers (F0017).

## Questions & Assumptions

Assumption (PRD): F0007 accepts original-currency money only. The Architect owns the canonical decimal encoding and the identifier-type normalization table; FEIN is the only normalization fixed here.

## Definition of Done

- [ ] Seven ACs pass with positive, boundary and rejection fixtures.
- [ ] Feature action records tests, coverage and required signoffs.
# Define name FactSlots

**Story ID:** F0007-S0005
**Feature:** F0007 — FactSlot model
**Title:** Define name FactSlots
**Priority:** High
**Phase:** MVP
**Status:** Done

## User Story

**As a** Rosa the Business Reviewer
**I want** an entity's legal, trade, former and informal names held as evidenced name facts on fixed slots
**So that** a named-insured change by endorsement keeps the same entity and both names remain answerable.

## Context & Background

ADR-0066 (Proposed, direction authorized 2026-09-25) has F0007 define the name FactSlots, F0013 declare the name properties and their kinds, F0017 resolve on them, and F0023 list them. The v0.1 P-2 scope guard admits storage, contract checks and hooks only. G1 (2026-11-09) deferred the display-name precedence rule to F0017/F0023.

## Acceptance Criteria

- [ ] **AC1:** The F0007 system-predicate set contains `hasLegalName` (`SINGLE`), `hasTradeName` (`MULTI`), `hasFormerName` (`MULTI`) and `knownAs` (`MULTI`). Resolving any of them with another cardinality is rejected with `CARDINALITY_CONFLICT`.
- [ ] **AC2:** EX-SEM-008: "Acme Roofing Inc." and "Acme Roofing & Restoration Inc." for the same entity resolve to the same `hasLegalName` slot. No new entity or slot is created. F0008/F0019 own the valid-time split.
- [ ] **AC3:** A name value carries the verbatim text, a normalized comparison form, an optional name-kind qualifier and a reference to its admitted F0006 name claim and quote. A name with no admitted evidence reference is rejected with `NAME_EVIDENCE_REQUIRED`.
- [ ] **AC4:** A trade name admitted only in KB A for a tenant entity associated with KBs A and B cannot be resolved, read or returned by the display-name hook in KB B. A KB B-only principal is denied, and the denial is indistinguishable from not found.
- [ ] **AC5:** The display-name hook returns the current accepted name facts of the reader's KB, each with its kind and slot. It applies no precedence (an open decision owned by F0017/F0023) and creates no `entity_alias` rows. Creating a name slot or member is authorized and audited like any slot (S0001).

## Interaction Contract

| Surface / Entry Point | User Action | Editable State | Save / Mutation Result | Reload / Persistence Evidence | Roles / Status Constraints |
|---|---|---|---|---|---|
| Slot resolution; display-name hook (internal read) | Resolve a name slot; list an entity's names in a KB | New name members only | Name slot/member with evidence reference; audit on create | Reload shows the same slot for both legal names; the KB B listing excludes KB A names | Existing KB read/write authority |

No screen. F0023 lists names later.

## Data Requirements

Name predicate keys and cardinalities, verbatim and normalized name text, name kind, and the F0006 name-claim/quote reference, all KB-owned.

## Role-Based Visibility

Names are visible only within their owning KB, even when the entity identity is shared across KBs. Shared identity never shares vocabulary.

## Non-Functional Expectations

No similarity matching or model call in F0007. Name normalization is deterministic and reversible to the stored verbatim text.

## Dependencies

S0001/S0002 identity and cardinality, and F0006 name-claim admission. F0013 adds name kinds, F0017 adds resolution and the alias projection, and F0023 adds display.

## Out of Scope

Display-name precedence, `entity_alias` projection, shared-name review pairs, similarity proposals (F0017/F0027), name ontology kinds (F0013) and temporal splitting (F0008/F0019).

## Questions & Assumptions

Open decision (G1, deferred): the order of preference across legal, trade and informal names for display. Recorded so no implementation invents one. Roles such as "the named insured" are F0006/F0017 role references, not name values.

## Definition of Done

- [ ] Five ACs pass, including the EX-SEM-008 identity fixture and the cross-KB negative case.
- [ ] Feature action records tests, coverage and required signoffs.
# Preserve pilot slots and ownership

**Story ID:** F0007-S0006
**Feature:** F0007 — FactSlot model
**Title:** Preserve pilot slots and ownership
**Priority:** Critical
**Phase:** MVP
**Status:** Done

## User Story

**As a** Ingrid the Persistence Engineer
**I want** the existing pilot slots, commit path and fact reads to keep working while every new slot identity row is owned by its tenant and knowledge base
**So that** adopting the full model loses no existing fact or history and opens no cross-tenant path.

## Context & Background

The F0001 pilot `fact_slot` (migration 0003) holds `entity_id` and a free-text `slot_type`, with a tenant ownership key to `entity_identity` added in 0006 and immutable ownership columns from 0007. The F0003 ownership table assigns `fact_slot` and `fact_slot_qualifier` to F0007 and requires preserving the 0003 rows. G1 (2026-11-09): F0007 binds ownership; F0018 designs and enables row-level security on every tenant-owned table.

## Acceptance Criteria

- [ ] **AC1:** Every pre-existing `fact_slot` row and its fact versions read back through `GET /facts/{factSlotId}` with identical values, ranges and evidence after the upgrade. No fact version is rewritten.
- [ ] **AC2:** Pilot slots that have no predicate key or qualifiers keep their `slot_type` and are labelled legacy. No predicate key or qualifier is fabricated for them. Identity-based resolution never matches a legacy slot implicitly; any mapping is explicit, recorded and reversible.
- [ ] **AC3:** The existing pilot commit, review and assertion-consumer test suites pass unchanged (regression).
- [ ] **AC4:** Every new F0007 row (qualifier, member, relationship) carries `tenant_id` and `knowledge_base_id` bound to its slot through composite foreign keys. A child row pointing at another tenant's or KB's slot is rejected by PostgreSQL. Updates to identity or ownership columns are rejected by trigger (the 0007 pattern).
- [ ] **AC5:** The F0007 tables are listed in an RLS inventory handed to F0018. F0007 does not enable row-level security and introduces no superuser, `BYPASSRLS` or table-owner shortcut that would stop F0018 enabling it.
- [ ] **AC6:** The migration is additive with a documented rollback. Upgrade, downgrade and upgrade again on a database seeded with pilot data leave pilot rows identical.
- [ ] **AC7:** Unauthorized or cross-tenant/KB slot reads are denied with zero disclosure. Existing authorization-decision audit is unchanged, and new slot creation is audited (S0001).

## Interaction Contract

| Surface / Entry Point | User Action | Editable State | Save / Mutation Result | Reload / Persistence Evidence | Roles / Status Constraints |
|---|---|---|---|---|---|
| Schema upgrade; existing `GET /facts/{factSlotId}` and pilot commit | Upgrade, read and commit on pilot slots | Pilot rows read-only to the migration | Additive structures only | Before/after snapshots equal; up/down/up cycle passes | Existing read/commit authority; operator runs migrations |

No screen or new route.

## Data Requirements

Legacy marker, preserved `slot_type`, composite ownership keys on every new child table, immutability triggers, and the RLS inventory list.

## Role-Based Visibility

Visibility is unchanged for pilot slots. New rows follow the parent slot's KB authorization.

## Non-Functional Expectations

Zero data loss and zero rewritten fact versions. The migration completes on the pilot dataset with no manual step.

## Dependencies

F0001 pilot migrations 0003/0006/0007, F0002 ownership pattern and F0003 safe schema evolution. F0018 receives the RLS inventory.

## Out of Scope

RLS policy design and enablement (F0018), isolation proof (F0026), and mapping pilot facts to ontology predicates (F0012/F0013).

## Questions & Assumptions

The Architect decides whether the pilot `slot_type` values get an explicit predicate-key mapping or remain legacy-only, under AC2's no-fabrication rule.

## Definition of Done

- [ ] Seven ACs pass with snapshot comparison, the migration cycle and ownership negative tests against PostgreSQL.
- [ ] Feature action records tests, coverage and required signoffs.
