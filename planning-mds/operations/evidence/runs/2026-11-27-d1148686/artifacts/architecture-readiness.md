### ARCH-01 — High: repeated session reads have no defined recoverable CSRF secret

- **Evidence:** `planning-mds/architecture/decisions/ADR-0082-bff-session-runtime-and-shell-foundation.md:63` (D5) defines one random 256-bit CSRF token per session, returned in `GET /session`; `:97` (D10) requires that response to carry it. `planning-mds/features/F0021-native-react-semantic-shell-and-oidc-session/migration-design.sql:49` stores only `csrf_digest`; `:45`–`:48` define the separate encrypted token carrier. `planning-mds/architecture/data-model.md:483`–`:487` (F0021 browser sessions) likewise specify encrypted OIDC tokens and a CSRF digest, without a recoverable CSRF carrier. `planning-mds/schemas/browser-session-v1.schema.json:84` requires the original synchronizer-token representation. `planning-mds/features/F0021-native-react-semantic-shell-and-oidc-session/feature-assembly-plan.md:190` (Bootstrap) obtains this body on page load, and `:203` refetches it after a CSRF failure. The target requirement is `planning-mds/features/F0021-native-react-semantic-shell-and-oidc-session/F0021-S0006-show-identity-and-knowledge-base-context-in-the-shell.md:22` (AC1).
- **Why it matters:** a one-way digest can validate a supplied secret but cannot produce it for the first session snapshot, a page reload, another worker or another tab. The plan does not say that the encrypted bundle also retains the CSRF secret, or define a deterministic derivation. Implementers must invent a security-sensitive persistence/derivation rule to make session bootstrap and subsequent mutations work. Rotating a new random token on every read would change the specified per-session contract and invalidate other tabs unless separately designed.
- **Repair owner:** architect, with backend-developer and Security review. Specify the recoverable or derivable per-session material, encryption/key handling and validation behavior, and align SQL/data-model/API design. Preserve server-side token handling and the defined per-session binding.
- **Required proof after repair:** repeated `GET /session` calls across reload, two workers and two tabs supply a usable token; both tabs can mutate with their current session token; re-authentication invalidates the previous session's token. Document this test expectation in the plan; observed results belong to the later feature run.

### ARCH-02 — High: an already-ended expired session loses its recoverable outcome

- **Evidence:** `planning-mds/architecture/decisions/ADR-0082-bff-session-runtime-and-shell-foundation.md:57` (D5 step 3) returns `401 unauthenticated` for every ended session, while only the request that discovers an idle/absolute timeout ends it and returns `401 session_expired`. `:71` (D6) separately promises that every waiter receives `session_expired` after failed renewal. `planning-mds/features/F0021-native-react-semantic-shell-and-oidc-session/migration-design.sql:53` retains explicit `idle_timeout`, `absolute_timeout` and `renewal_failed` reasons, but no request-path rule maps these terminal reasons back to the recoverable code. `planning-mds/features/F0021-native-react-semantic-shell-and-oidc-session/feature-assembly-plan.md:198`–`:202` (API client) queues work and opens the restoration dialog only for `session_expired`. Requirements: `planning-mds/features/F0021-native-react-semantic-shell-and-oidc-session/F0021-S0002-protect-cookie-authenticated-calls-with-csrf-and-origin-checks.md:25` (AC4), `F0021-S0003-renew-once-and-bound-session-lifetime.md:23`–`:25` (AC2–AC4, in the same feature folder), and `F0021-S0004-re-authenticate-without-losing-work-or-replaying-mutations.md:22`–`:24` (AC1–AC3, same folder).
- **Why it matters:** if a status poll, another tab or the renewal owner ends the session first, a subsequent user mutation or waiter sees `unauthenticated` rather than the outcome that preserves and reconfirms its work. The design's unconditional ended-session branch conflicts with its stable expired-session and all-waiters promises. It does not define a common recovery path for this ordinary ordering.
- **Repair owner:** architect, with backend-developer and frontend-developer. Define a consistent terminal-state-to-response mapping, including how long timeout/renewal-ended sessions remain recognizable, and align the shell's handling. Keep explicit logout/replacement/unknown-session behavior separate where requirements call for it; do not add automatic mutation replay.
- **Required proof after repair:** two-worker renewal failure returns the specified recoverable result to every waiter; a background poll or another tab ending a timed-out session first does not prevent a later blocked mutation from retaining input and requiring explicit re-confirmation. Repeat for idle, absolute and renewal-failed endings and verify that logout remains signed out.

### ARCH-03 — High: IdP end-session failure has no observable completion/result contract

- **Evidence:** `planning-mds/features/F0021-native-react-semantic-shell-and-oidc-session/F0021-S0005-log-out-with-upstream-revocation-and-cache-hygiene.md:28` (AC7) requires end-session failure to be reported like AC3 (`:24`), and `:40` requires an end-session outcome record. `planning-mds/architecture/decisions/ADR-0082-bff-session-runtime-and-shell-foundation.md:77`–`:80` (D7) writes the logout outcome, returns an end-session URL, stores the outcome in `sessionStorage` and navigates away. `planning-mds/schemas/logout-result-v1.schema.json:110`–`:129` allows only `redirect` or `unavailable`, not a completed/failed/unknown execution result. `planning-mds/features/F0021-native-react-semantic-shell-and-oidc-session/bff-api-design.yaml:79`–`:99` supplies the initial logout result but no completion reporting path. `planning-mds/features/F0021-native-react-semantic-shell-and-oidc-session/feature-assembly-plan.md:295` (S0005 AC7 proof) tests next-sign-in credentials and missing discovery, without a failure of the advertised end-session endpoint.
- **Why it matters:** successful refresh-token revocation and the existence of an end-session URL do not establish that the subsequent browser navigation ended the IdP session. If that endpoint errors, becomes unreachable or never completes, the plan defines neither how the shell observes/reports the result nor how the required durable outcome is updated. The declared schema can report initiation or missing capability, but cannot represent the required actual failure. This is separate from the adequately specified revocation-endpoint failure path.
- **Repair owner:** architect with product-manager and Security. Define the end-session lifecycle, observable completion/failure or bounded unknown outcome, corresponding response/UI/audit representation, and the failure behavior. If reliable observation is intentionally excluded, route an explicit requirement reconciliation through plan ownership rather than claiming AC7 satisfied.
- **Required proof after repair:** force the discovered end-session endpoint to fail or not complete after refresh-token revocation succeeds, and verify the agreed warning/result and durable record. Also retain the success and missing-discovery cases; do not require runtime results at this planning gate.
