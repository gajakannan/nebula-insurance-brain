22: - [x] **AC1:** Every valid-time bound on an identity-v1 commit carries a granularity in {`YEAR`, `QUARTER`, `MONTH`, `DAY`, `HOUR`, `MINUTE`, `SECOND`} and an IANA zone name. 25: - [x] **AC4:** A `DAY` start of 2026-06-01 in `America/Chicago` reads back as 2026-06-01 in that zone, never 2026-05-31. A round trip through commit and read preserves the instant, granularity and zone exactly, for every granularity.
26: - [x] **AC5:** The start and the end of one version may have different granularities. Each is validated against its own granularity and zone.
27: - [x] **AC6:** The version-row design can represent a point (`EVENT`) and no valid time (`ETERNAL`) without further DDL. Until F0012/F0013 declare `temporal_kind`, every slot is treated as `STATE` (Assumption A2).

Afterwards every (valid, known) coordinate on a dense grid over the affected range resolves to at most one version. Each winning commit writes exactly one commit audit event and one outbox event.

25: - [x] **AC4:** A RELATIONSHIP slot's versions obey the same exclusion and close behaviour as a SINGLE slot, without a separate relationship version table unless Phase B records why one is needed.
26: - [x] **AC5:** For identity-v1 slots, the database rejects a version whose `fact-answer/v1` envelope has a value with a non-`PRESENT` state, or `PRESENT` without a value (F0007 S0003 AC2 backstop). A direct insert that bypasses the service is rejected. Legacy pilot versions are not subject to this check.
27: - [x] **AC6:** A version, change row or commit row whose tenant or knowledge base differs from its slot's is rejected by composite-key constraints, with zero rows written.
